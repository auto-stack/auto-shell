## 第一步：补全 Plan 024 的 deferred 项 + 030 的 M0 验证

### 关键发现（调研结论）
Plan 024 有两个 deferred 项，但调研发现一个**更根本的问题**：
- `&&` 复合谓词**端到端完全失效**（实测 `.type=="file" && .size>0` 输出 0，单谓词输出 2）。根因：`&&` 被底层 `parse_chain`（pipeline.rs:68-81）当作命令链操作符切分，DSL 谓词到不了 `parse_pipe_stage`。单元测试通过只因绕过了 `parse_chain`。
- `||` 面临**完全相同**的语法抢夺。

### 设计决策：复合谓词改用 `and`/`or` 关键字
放弃 `&&`/`||` 语法，DSL 谓词改用 `and`/`or`：
```
ls | .type == "file" and .size > 0          # 且（原 FilterAll）
ls | .type == "dir" or .name contains "log"  # 或（新 FilterAny）
```
**理由**：①零架构冲突——`and`/`or` 是普通标识符，`parse_chain` 只切 `&&`/`||`/`|` 符号，不碰 `and`/`or`；②符合 Nushell/jq/SQL 惯例；③现有 `&&` 本就端到端失效，无用户依赖。

## 任务 A：嵌套字段访问 `.user.name`

**改 3 处（operators.rs）+ 4 处（pipe_stages.rs）**

1. **operators.rs `get_field`（line 276-282）**：改为按 `.` 分割递归取字段：
   ```rust
   fn get_field(item: &Value, field: &str) -> Value {
       let mut cur = item;
       for part in field.split('.') {
           cur = match cur {
               Value::Obj(obj) => obj.get(part).unwrap_or(Value::Nil),
               _ => return Value::Nil,
           };
       }
       cur.clone()
   }
   ```
   一处改动覆盖 Filter/FilterAll/SortBy/Map/GroupBy/Sum/Avg/Min/Max（都用 get_field）。

2. **operators.rs `Select`（line 180）**：当前直接 `obj.get(f)`，改为复用 `get_field` 支持嵌套投影。

3. **pipe_stages.rs 4 处 `take_while`**（line 87/115/145/180）：字段名字符集加入 `.`：
   ```
   take_while(|c| c.is_alphanumeric() || *c == '_' || *c == '-' || *c == '.')
   ```
   让 `.user.name` 能被完整解析（而非停在 `user`）。提取一个 `is_field_char` 辅助函数避免重复。

## 任务 B：`and`/`or` 复合谓词

**operators.rs + pipe_stages.rs**

1. **operators.rs 新增 `FilterAny` 变体**（与 FilterAll 对称）：
   ```rust
   /// `.f1 op1 v1 || .f2 op2 v2` → any condition holds.
   FilterAny { conditions: Vec<(String, CmpOp, Value)> },
   ```
   `apply` 实现：`conditions.iter().any(|...| compare(...))`（对称于 FilterAll 的 `.all()`）。

2. **pipe_stages.rs 重构 `parse_dot_stage`/`parse_compound_filter`**：
   - 入口判断（line 70-76）：检测 `" and "` 或 `" or "` → 走复合解析。
   - `parse_compound_filter` 改为接收分隔符参数，按 `" and "`→FilterAll、`" or "`→FilterAny。
   - **混合优先级**（YAGNI 决策）：`a and b or c` 暂不支持混合优先级（需谓词 AST 树）。如检测到同时含 `and` 和 `or`，返回 None（退化为普通命令处理，不误解析）。文档注明混合表达式是未来项。纯 `and` 链或纯 `or` 链完整支持。

3. **移除 `&&` 的复合谓词解析**：`parse_compound_filter` 不再处理 `" && "`（该路径已端到端失效，是死代码）。
